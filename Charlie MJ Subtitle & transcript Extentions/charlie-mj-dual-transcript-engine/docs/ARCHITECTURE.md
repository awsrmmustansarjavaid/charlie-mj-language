# Architecture

## Goal

Build a small, independent dual-transcript engine that can later be embedded into a larger Charlie MJ Language extension without duplicating YouTube caption fetching.

## Pipeline

```text
YouTube player
    |
    | native caption request
    v
MAIN-world request observer
    |
    v
working timedtext URL
    |
    +--> complete original JSON3 track
    |
    +--> complete YouTube translated JSON3 track (tlang)
    |
    v
cue parser
    |
    v
raw synchronized cue model
    |
    +--> sentence merger
    |
    +--> timeline engine
    |
    +--> complete transcript UI
    |
    +--> dual subtitle UI
```

## Why request interception is isolated

YouTube caption endpoints can change and can require dynamic request parameters. The engine does not invent a token. It observes the URL the YouTube player is already using, then reuses that URL to request the complete JSON3 caption track.

## Why JSON3

JSON3 preserves timed caption events and segment text in a compact structure that is easy to normalize. The extension immediately converts it to its own cue representation so no other module depends on YouTube's raw response format.

## Why two cue layers

`cues` retain timing precision. `sentences` provide readable transcript units. This prevents a UI requirement for readable sentences from damaging synchronization accuracy.

## Why binary search + requestAnimationFrame

The player exposes `currentTime`. A binary search locates the active cue without scanning every cue. `requestAnimationFrame` keeps the UI responsive and closely follows playback without requiring a heavy synchronization library.

## Why no translation API in v1

The first objective is to validate a reliable, direct-to-YouTube dual transcript fetcher. If YouTube itself can produce the translated caption track, no external translation request is necessary. A future optional translation adapter can be added behind the same engine boundary without changing the core fetcher.

## Integration target

The future Charlie MJ Language extension should import/adapt the normalized transcript object and never implement a second YouTube caption downloader.


## v1.0.0 dual-track fetch hardening

The extension now installs `src/inject.js` as a Manifest V3 `MAIN`-world content script at `document_start`. This is important because YouTube may issue its caption request before an asynchronously injected bridge exists. The bridge therefore starts early enough to observe the real YouTube timedtext request, including current proof/signature parameters.

The content script then performs two complete-track requests using the captured YouTube URL:

1. Original caption track (`fmt=json3`).
2. YouTube-native translated caption track (`tlang=<target>&fmt=json3`).

The result is aligned locally and cached. No sentence-by-sentence third-party translation service is used. If the translation track is unavailable, the original transcript remains usable and the panel explicitly reports the translation failure instead of pretending a dual transcript exists.

The transcript panel is independently rendered from the same cue store and can be opened from the floating `DT` button or the YouTube player `DT` button.

## v1.0.0 dual-fetch reliability fix

The YouTube fetching path is deliberately owned by `src/inject.js` in the MAIN world. The bridge first observes a real player `/api/timedtext` request through Resource Timing (and supplementary fetch/XHR hooks), preserving the proof-of-origin parameters generated by YouTube. It then merges the selected caption track parameters onto that working request and fetches the complete original JSON3 track and the complete YouTube-native translated JSON3 track with `tlang=<target>`. The isolated `content.js` only receives parsed cue data and is responsible for rendering, caching, searching, and timeline synchronization.

This avoids treating the player response `baseUrl` as a guaranteed working URL: current YouTube responses can omit the request-time proof parameters from that value.
